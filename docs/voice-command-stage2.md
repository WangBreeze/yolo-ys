# 第二阶段：教程语音转候选游戏命令

## 目标与边界

第二阶段读取第一阶段产生的带时间语音和候选语义，把“往东北走、拿神瞳、与 NPC 对话”整理成可校验的语义命令，再编译为项目已有的 `Plan`。它不直接把一句旁白变成固定键盘时序，也不在 Linux 上操作游戏。

推荐链路：

```text
带时间语音 + 分段画面语义
        ↓
游戏词典纠错与证据对齐
        ↓
候选语义命令（目标、方向、交互、前置/结果、来源时间）
        ↓
人工复核
        ↓
版本化 Plan
        ↓
Windows 当前画面感知 → 策略 → dry-run → 有限实机输入
```

语音只说明意图或目标，不能证明动作已经执行，也通常不能给出可靠的按键持续时间。固定坐标和旧画面位置不写进命令；目标应保存为语义标签，并在当前窗口画面中重新定位。

## 当前已经具备的环境

| 条件 | 当前状态 | 说明 |
|---|---|---|
| Python 与本地视频环境 | 已具备 | Python 3.12、项目 `.venv`、ffmpeg/ffprobe、OpenCV。 |
| 本地语音模型 | 已具备 | `faster-whisper-small`，输出带起止时间的中文转录。 |
| 本地语义模型 | 已具备 | `Qwen3-VL-2B-Instruct`，CUDA 推理；视频和转录无需上传。 |
| 真实教程素材 | 已具备 | `BV1P6SNYREo8` 的 20 个分P和分段候选语义已经生成。 |
| 计划和动作协议 | 部分具备 | 已有版本化 `Plan`、`Step`、`Action`、超时、重试和来源时间。 |
| 执行闭环 | 已具备框架 | 当前状态驱动 planner/policy/controller，动作后必须观察结果。 |

当前 Linux 机器足以开发和验证“语音到候选命令”以及 Plan 静态校验。只有进入当前游戏画面识别和真实输入时才需要 Windows。

## 当前实现

项目已经提供 `semantic-command` schema v1、静态校验器和原神词典 `configs/genshin-command-lexicon.json`。词典当前包含 28 个高层命令，参考 BetterGI 提交 `f29966868c6e2d5b8798bb6a4f3df201ec4a5f95` 中的动作枚举、寻路模式、动作处理器、输入释放和界面状态判断；BetterGI 只作为只读设计参考，没有被复制为运行依赖。

```bash
python -m game_agent list-commands
python -m game_agent extract-commands <第一阶段报告.json> --output <候选命令.json>
python -m game_agent check-commands <候选命令.json>
```

提取器会保留原始语音、起止时间、对应语义分段和模型来源，并把“保险/保箱/保鲜/暴江”等识别结果按词典纠正为“宝箱”。输出状态固定为 `candidate_commands`，命令参数禁止出现 `key`、绝对坐标和按键持续时间。

本机已为 `BV1P6SNYREo8` 的 P1–P20 生成 674 条候选命令，其中 54 条保存了纠错记录；每个文件都通过 schema 和词典校验。P1 是前置说明，没有生成执行命令。汇总位于 `memory/commands/BV1P6SNYREo8/index.json`，可跨环境提交的 P10 表格位于 [P10 复核表](reviews/BV1P6SNYREo8/P10.md)。这些数量反映规则命中，不代表 674 条都已经人工确认，也不代表能够在游戏里执行。

## 开始生成命令前必须确定的条件

### 1. 游戏身份和 UI profile

必须填写真实的游戏 ID、实际版本或 build、语言、分辨率、窗口模式、UI 缩放、输入设备和自定义键位。任意关键设置变化都应产生新的 `game.version` 或 `game.profile`，不能复用旧计划的已验证状态。

### 2. 游戏命令词典

先定义有限的语义命令集合，例如：

- `open_map`、`select_waypoint`、`teleport`；
- `move_toward`、`climb`、`jump`、`glide`；
- `interact`、`talk_to`、`collect`、`open_chest`；
- `transform_saurian`、`scan_graffiti`、`activate_mechanism`；
- `fight_until_clear`、`wait_until`、`inspect_inventory`。

每个命令需要参数约束、允许出现的目标类别、可观察的前置条件和完成条件。模型遇到词典外内容时应输出 `unsupported` 或 `needs_review`，不能临时创造键名或动作。

### 3. 原神专有词纠错表

第一阶段已经观察到稳定的语音误识别：

- 神瞳 → 山头、神头；
- 宝箱 → 保险、宝虾；
- 涂鸦 → 图鸭；
- 传送锚点 → 传统帽点；
- 地灵龛 → 地零开、地灵坎。

纠错必须结合游戏词典、画面和上下文，并保留原始转录。无法确认的任务名、物品名和数字不得自动改成确定事实。

### 4. 可观察状态

每个 Plan 步骤都要求非空的可观察结果。至少需要定义：

- 当前界面：游戏世界、地图、背包、对话、挑战；
- 目标是否可见、是否已交互；
- 宝箱锁定/已开启、敌人存在/已清除；
- 任务追踪、挑战开始/完成、奖励或成就提示；
- 角色状态：普通、攀爬、滑翔、龙魂变身；
- 失败状态：死亡、掉落、卡住、错误菜单、加载中。

这些事实必须由 Windows 当前画面的 perception 插件提供。仅靠语音不能判定步骤已经完成。

### 5. 动作能力

现有 Action v1 只支持最长 1 秒的短时单键、左键点击、相对鼠标移动和等待。它可以覆盖菜单、对话和简单交互；开放世界移动还需要后续能力：

- 按键按下、保持、释放；
- 组合键或同时移动；
- 连续镜头控制；
- 滚轮和更多鼠标按钮；
- 有界的移动、攀爬和滑翔控制器；
- 按当前状态中断并释放全部输入。

第二阶段先保存高层语义命令，避免过早把长路线固化成动作 v1 的大量短按键。

### 6. 人工复核数据

至少需要对一小批命令逐条确认原始语音、来源时间、画面证据、命令类型、前置条件和完成条件。未复核的命令只能保持 `candidate`，不能进入实机 live，也不能写入已验证动作经验。

## Windows 执行环境

进入 dry-run 前，需要：

- Windows 10/11、Python 3.11 或 3.12；
- 安装项目的 `windows` 与实际感知模型依赖；
- 游戏使用固定的窗口化或无边框模式，窗口标题/类可精确匹配；
- 固定分辨率、DPI 和 UI 缩放；
- 目标游戏 build、语言和键位与 profile 一致；
- 已验证的 YOLO/OCR/规则感知插件及对应类别；
- 代理进程与游戏处于可兼容的权限级别；
- F12 和 `memory/STOP` 能停止流程，异常路径会释放全部输入。

首次 Windows 验证顺序：窗口信息 → 客户区截图 → 目标定位 dry-run → 单个无破坏动作 → 观察结果 → 小型闭环。未通过前不运行整条视频路线。

## 第二阶段验收门槛

1. 每条候选命令有来源视频、时间范围、原始语音和模型版本。
2. 命令只使用版本化词典；未知目标保留未知，不生成虚构键位。
3. 每个可执行步骤都有可观察前置条件、完成条件、超时和失败处理。
4. 编译后的 Plan 通过 schema、游戏/profile、允许键和来源时间校验。
5. 人工复核状态与模型候选状态分开保存。
6. Linux simulation 和 Windows dry-run 不产生真实输入或“已学会”记录。
7. 只有 Windows 当前画面确认动作结果后，轨迹才有资格进入经验学习。

## 当前缺口与实施顺序

1. 人工复核 P10 的候选命令，合并同一句中的复合意图，标出误命中与缺失命令。
2. 为复核命令定义当前画面可观察的前置条件和完成条件；证据不足时保留 `needs_review`。
3. 实现只接受 `reviewed` 命令的 Plan v1 编译器，并做来源时间、游戏/profile、超时和失败处理校验。
4. 在 Linux simulation/dry-run 验证命令、Plan 和来源追踪，不产生真实输入。
5. 准备 Windows 的真实 build/profile、窗口、键位和感知模型。
6. Windows 先做目标定位 dry-run，再扩展动作协议并进行有限实机闭环。

当前可立即开始第 1–4 项。第 5–6 项需要目标 Windows 游戏环境和用户实际配置。
